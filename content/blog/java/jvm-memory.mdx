
# JVM 메모리 구조 완벽 가이드: Heap, Stack, Method Area 심층 분석

운영 중인 서버에서 갑자기 `OutOfMemoryError: Java heap space`가 터졌습니다. 로그를 뒤져봐도 원인을 알 수 없고, 트래픽이 몰리는 시간대마다 반복됩니다. 이런 상황에서 JVM 메모리 구조를 모르면 원인 파악조차 불가능합니다.

이 글에서는 JVM의 런타임 데이터 영역을 구성하는 핵심 요소들을 코드와 함께 상세히 분석하고, 실무에서 자주 발생하는 메모리 문제의 원인과 해결법까지 다룹니다.

## 1. JVM 런타임 데이터 영역 전체 구조

JVM이 OS로부터 할당받은 메모리 영역을 런타임 데이터 영역(Runtime Data Area)이라고 합니다. 이 영역은 **스레드 간 공유 영역**과 **스레드별 독립 영역**으로 나뉩니다.

![JVM Memory Architecture Diagram](assets/images/blog/jvm_memory.webp)
*(이미지 설명: Method Area와 Heap은 모든 스레드가 공유하며, Stack, PC Register, Native Method Stack은 스레드마다 생성됩니다.)*

| 영역 | 공유 범위 | 저장 대상 | GC 대상 |
|---|---|---|---|
| Method Area | 모든 스레드 공유 | 클래스 메타데이터, static 변수, 상수 풀 | Metaspace(Java 8+)에서 관리 |
| Heap | 모든 스레드 공유 | new로 생성된 객체, 배열 | GC의 주요 대상 |
| JVM Stack | 스레드별 독립 | 지역 변수, 매개변수, 리턴 값 | 메서드 종료 시 자동 해제 |
| PC Register | 스레드별 독립 | 현재 실행 중인 JVM 명령 주소 | 해당 없음 |
| Native Method Stack | 스레드별 독립 | C/C++ 네이티브 코드 실행 정보 | 해당 없음 |

## 2. Heap Area 심층 분석: GC의 전쟁터

Heap은 성능 튜닝의 핵심입니다. 모든 객체가 이곳에 생성되고, GC가 이곳을 청소합니다.

### 2.1 세대별 메모리 구조 (Generational GC)

HotSpot JVM은 "대부분의 객체는 금방 죽는다"는 약한 세대 가설(Weak Generational Hypothesis)에 기반해 Heap을 세대별로 나눕니다.

```java
public class HeapDemo {
    public static void main(String[] args) {
        // 이 객체는 Eden에 생성됨
        byte[] shortLived = new byte[1024 * 1024]; // 1MB

        // shortLived가 더 이상 참조되지 않으면 Minor GC에서 수거됨
        shortLived = null;

        // 아래 객체는 오래 살아남아 Old Generation으로 승격(Promotion)
        List<String> longLived = new ArrayList<>();
        for (int i = 0; i < 100_000; i++) {
            longLived.add("item-" + i);
        }
    }
}
```

**Young Generation** 내부는 다시 세 구역으로 나뉩니다.

- **Eden**: 새 객체가 최초 할당되는 곳. Eden이 가득 차면 Minor GC 발생
- **Survivor 0 / Survivor 1**: Minor GC에서 살아남은 객체가 이동. 두 영역 중 하나는 항상 비어 있음
- **Old Generation**: Survivor에서 일정 age(기본 15)를 넘긴 객체가 승격되는 곳. Full GC의 대상

### 2.2 GC 종류와 Stop-the-World

| GC 종류 | 대상 영역 | 특징 |
|---|---|---|
| Minor GC | Young Generation | 빠르고 자주 발생 (수~수십 ms) |
| Major GC (Full GC) | Old Generation + Young | 느리고 STW(Stop-the-World) 발생 |

Full GC가 발생하면 모든 애플리케이션 스레드가 멈춥니다. 이것이 바로 운영 환경에서 응답 지연의 주범입니다.

```bash
# JVM 힙 크기 설정 예시
java -Xms512m -Xmx2g -XX:NewRatio=2 -jar app.jar

# -Xms: 초기 힙 크기
# -Xmx: 최대 힙 크기
# -XX:NewRatio=2: Old/Young 비율 (Old가 Young의 2배)
```

### 2.3 GC 알고리즘 선택 가이드

```bash
# G1GC (Java 9+ 기본값, 범용적)
java -XX:+UseG1GC -jar app.jar

# ZGC (Java 15+, 초저지연 목표, 10ms 이하 STW)
java -XX:+UseZGC -jar app.jar
```

실무에서는 **G1GC**가 대부분의 워크로드에 적합합니다. 초저지연이 필요한 금융/게임 서버라면 **ZGC**를 고려하세요.

## 3. Stack Area: 메서드 호출의 기록장

각 스레드는 고유한 JVM Stack을 가집니다. 메서드가 호출될 때마다 **스택 프레임(Stack Frame)**이 push되고, 메서드가 종료되면 pop됩니다.

```java
public class StackDemo {
    public static void main(String[] args) {
        // main 프레임이 스택에 push됨
        int result = add(3, 5);
        // add 프레임은 이미 pop되어 사라짐
        System.out.println(result);
    }

    static int add(int a, int b) {
        // add 프레임이 스택에 push됨
        // a=3, b=5는 이 프레임의 지역 변수 배열에 저장
        int sum = a + b; // sum도 지역 변수 배열에 저장
        return sum;
        // 메서드 종료 → 프레임 pop
    }
}
```

### StackOverflowError 재현과 해결

```java
// 종료 조건 없는 재귀 → StackOverflowError
public static int badFactorial(int n) {
    return n * badFactorial(n - 1); // 종료 조건 없음!
}

// 올바른 재귀
public static int factorial(int n) {
    if (n <= 1) return 1; // 종료 조건 필수
    return n * factorial(n - 1);
}
```

스택 크기는 `-Xss` 옵션으로 조절 가능하지만, 대부분의 경우 코드의 재귀 깊이를 줄이는 것이 근본적인 해결책입니다.

```bash
# 스레드당 스택 크기를 1MB로 설정
java -Xss1m -jar app.jar
```

## 4. Method Area와 Metaspace

Java 8 이전에는 Method Area가 PermGen(Permanent Generation)으로 구현되어 고정 크기 제한이 있었습니다. Java 8부터는 **Metaspace**로 변경되어 네이티브 메모리를 사용합니다.

```bash
# Metaspace 크기 제한 (기본값: 무제한 → 서버에서는 반드시 설정)
java -XX:MaxMetaspaceSize=256m -jar app.jar
```

Metaspace에 저장되는 것들:
- 클래스의 구조 정보 (필드, 메서드, 접근 제어자 등)
- 런타임 상수 풀 (Runtime Constant Pool)
- static 변수 (참조형의 경우 실제 객체는 Heap에)

## 5. 실무 트러블슈팅: 메모리 문제 진단

### 5.1 Heap Dump 분석

`OutOfMemoryError`가 발생했을 때 가장 먼저 해야 할 일은 힙 덤프를 확보하는 것입니다.

```bash
# OOM 발생 시 자동으로 힙 덤프 생성 (운영 서버 필수 설정)
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/log/heapdump.hprof \
     -jar app.jar
```

### 5.2 흔한 메모리 누수 패턴 3가지

```java
// 패턴 1: Static 컬렉션에 무한 축적
public class LeakExample {
    private static final List<byte[]> cache = new ArrayList<>();

    public void process() {
        cache.add(new byte[1024 * 1024]); // 매 호출마다 1MB 축적
    }
}

// 패턴 2: 닫지 않은 리소스
public void readFile() {
    InputStream is = new FileInputStream("data.txt");
    // is.close()를 호출하지 않음 → 리소스 누수
}

// 해결: try-with-resources 사용
public void readFileSafe() {
    try (InputStream is = new FileInputStream("data.txt")) {
        // 자동으로 close 호출됨
    } catch (IOException e) {
        log.error("파일 읽기 실패", e);
    }
}
```

**패턴 3: 리스너/콜백 미해제** — 이벤트 리스너를 등록한 뒤 해제하지 않으면, 리스너가 참조하는 객체까지 GC 대상에서 제외됩니다.

### 5.3 운영 서버 권장 JVM 옵션

```bash
java -Xms2g -Xmx2g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/log/heap.hprof \
     -Xlog:gc*:file=/var/log/gc.log:time \
     -jar app.jar
```

`-Xms`와 `-Xmx`를 동일하게 설정하면 JVM이 힙 크기를 동적으로 조절하는 오버헤드를 줄일 수 있습니다.

## 결론: 핵심 체크리스트

JVM 메모리 구조를 이해하는 것은 안정적인 서버 운영의 기본입니다. 정리하면:

1. **Heap**: 객체가 살고 죽는 곳. GC 튜닝의 핵심. `-Xms`/`-Xmx`로 크기를 관리하세요.
2. **Stack**: 메서드 호출의 흐름을 기록. 재귀 깊이를 주의하세요.
3. **Method Area(Metaspace)**: 클래스 메타데이터 저장소. 동적 클래스 로딩이 많으면 모니터링 필수.
4. **운영 서버에서는** 반드시 `HeapDumpOnOutOfMemoryError`와 GC 로그를 활성화하세요.

트래픽이 많은 시스템에서는 Heap 덤프 분석과 GC 로그 모니터링이 필수입니다. 오늘 다룬 내용을 바탕으로, 본인의 운영 서버 JVM 옵션부터 점검해 보시길 권장합니다.
