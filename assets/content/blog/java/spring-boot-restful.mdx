# Spring Boot에서 RESTful API 만들기: 설정부터 작성 패턴까지

_작성일: 2026-02-09_

RESTful API는 **URL로 자원(Resource)**, **HTTP 메서드로 행위(Action)**를 표현해 일관된 인터페이스를 만드는 방식입니다. Spring Boot는 REST에 필요한 구성(Jackson, 내장 서버, MVC)을 기본값으로 제공해 빠르게 시작할 수 있습니다. 이 글에서는 Boot 환경에서 REST API를 만들 때 필요한 **설정(의존성/JSON/검증/예외 처리)**과 **메서드별 URL 양식**, 그리고 실무에서 자주 헷갈리는 포인트(PUT vs PATCH, 여러 ID/필터 처리)를 예시와 함께 정리합니다.

![Spring Boot REST API](assets/images/blog/spring_boot_rest.webp)

## 1) 기본 설정: 의존성과 프로젝트 준비

Spring Boot에서 REST API를 만들 때 가장 기본은 `spring-boot-starter-web`입니다.

```gradle
dependencies {
  implementation 'org.springframework.boot:spring-boot-starter-web'
  implementation 'org.springframework.boot:spring-boot-starter-validation'
  testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
```

- `starter-web`: `@RestController`, Jackson(JSON), 내장 톰캣 등 REST에 필요한 기본 묶음
- `starter-validation`: `@Valid`로 요청 DTO 검증(Bean Validation)

### (추가) 기본 설정 파일 예시

요청/응답 로깅이나 JSON 네이밍 같은 “팀 기본값”은 `application.yml`로 통일하는 게 좋습니다.

```yaml
server:
  port: 8080

spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```

## 2) 작성 패턴(핵심만)

- **Controller는 얇게**: HTTP 입출력만 처리하고, 규칙은 Service로
- **DTO 분리**: 엔티티 노출 대신 Request/Response DTO로 계약 고정
- **검증**: `@Valid` + `starter-validation`으로 요청값을 초기에 차단

간단한 계층 예시는 아래처럼 생각하면 됩니다.

```text
Controller(HTTP) → Service(규칙/트랜잭션) → Repository(DB)
```

## 3) RESTful하게 설계하는 규칙(실무 체크리스트)

### (1) URL은 자원 중심으로

- 좋은 예: `GET /users/1`, `POST /users`, `PUT /users/1`
- 덜 좋은 예: `POST /createUser`, `GET /getUser`

### (2) 메서드별 선언 & URL 양식(예시)

REST는 보통 “목록 URL”과 “단건 URL”을 나눕니다.

| 메서드 | URL 양식 | 의미 | Spring Boot 선언 | 파라미터 받기(예시) |
|---|---|---|---|---|
| GET | `/api/v1/users` | 목록 조회(페이징/필터) | `@GetMapping` | `@RequestParam int page, int size` / 여러 값: `@RequestParam List<Long> ids` |
| GET | `/api/v1/users/{id}` | 단건 조회 | `@GetMapping("/{id}")` | `@PathVariable Long id` |
| POST | `/api/v1/users` | 생성 | `@PostMapping` | `@RequestBody CreateUserRequest body` |
| PUT | `/api/v1/users/{id}` | 전체 교체(멱등) | `@PutMapping("/{id}")` | `@PathVariable Long id, @RequestBody UpdateUserRequest body` |
| PATCH | `/api/v1/users/{id}` | 부분 수정 | `@PatchMapping("/{id}")` | `@PathVariable Long id, @RequestBody PatchUserRequest body` |
| DELETE | `/api/v1/users/{id}` | 삭제(멱등) | `@DeleteMapping("/{id}")` | `@PathVariable Long id` |

#### `id` 값을 실제로 “받아서 쓰는” 방법

```java
@GetMapping("/{id}")
public UserResponse get(@PathVariable Long id) {
  return userService.getById(id);
}
```

#### 값을 여러 개 받을 때(대표 패턴 2가지)

1) **PathVariable 여러 개**: 리소스가 계층 구조일 때

```java
@GetMapping("/users/{userId}/orders/{orderId}")
public OrderResponse getOrder(
  @PathVariable Long userId,
  @PathVariable Long orderId
) { /* ... */ }
```

2) **QueryParam 여러 개**: 필터/검색/배치 조회일 때

```java
@GetMapping
public List<UserResponse> list(@RequestParam List<Long> ids) { /* ... */ }
// 호출 예: /api/v1/users?ids=1&ids=2&ids=3
```

> 팁: “여러 ID로 조회”가 핵심 요구라면 `/users:batchGet` 같은 RPC 스타일 대신, 위처럼 QueryParam으로 해결하면 REST 스타일을 유지하기 쉽습니다.

> 참고: 사용자가 “push”라고 말하는 경우가 있는데, REST 표준 HTTP 메서드는 **POST**입니다.

### (3) 상태코드를 명확히

- 생성 성공: `201 Created`
- 잘못된 요청: `400 Bad Request`
- 리소스 없음: `404 Not Found`

Spring에서는 `ResponseEntity`로 상태코드와 헤더를 명시할 수 있습니다.

#### `POST`에서 Location 헤더 주기(권장)

```java
@PostMapping
public ResponseEntity<UserResponse> create(@Valid @RequestBody CreateUserRequest req) {
  var created = userService.create(req);
  return ResponseEntity
    .created(URI.create("/api/v1/users/" + created.id()))
    .body(created);
}
```

### (4) PUT vs PATCH, 언제 쓰나?

- **PUT**: 리소스를 “전체 교체”하는 의미. 같은 요청을 여러 번 보내도 결과가 같아야(멱등) 합니다.
- **PATCH**: 일부 필드만 변경. 변경 필드가 많지 않거나 부분 업데이트가 잦을 때 유리합니다.

실무에서는 “사용자 프로필 전체 수정” 같은 화면은 PUT, “알림 설정 한 개 토글” 같은 화면은 PATCH로 구분하는 편이 자연스럽습니다.

## 4) 예외 처리: API 품질을 좌우하는 핵심

REST API는 실패했을 때도 “읽기 쉬운 규격화된 응답”을 주는 것이 중요합니다. Spring Boot에서는 `@RestControllerAdvice`로 전역 예외 처리를 구성합니다.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
    return ResponseEntity.badRequest().body(ErrorResponse.of("VALIDATION_ERROR", "요청값이 올바르지 않습니다."));
  }
}

public record ErrorResponse(String code, String message) {
  static ErrorResponse of(String code, String message) { return new ErrorResponse(code, message); }
}
```

검증 오류(400)가 발생했을 때, 프론트가 메시지를 바로 표시할 수 있도록 `code/message` 구조를 통일해두면 운영이 편해집니다.

## 5) 실전 팁(최소 세트)

- **버전**: `/api/v1` 등 규칙을 초기에 고정
- **페이징**: 목록 API는 `page/size/sort` 표준화

예를 들어 목록 API는 아래처럼 “기본값”을 두고 확장합니다.

```java
@GetMapping
public Page<UserResponse> list(
  @RequestParam(defaultValue = "0") int page,
  @RequestParam(defaultValue = "20") int size,
  @RequestParam(required = false) String q
) { /* ... */ }
```

## 결론

Spring Boot REST API의 핵심은 **규칙과 구조(계층 분리, DTO, 예외 처리)**입니다. URL/메서드 규칙과 오류 응답 포맷을 먼저 고정하고, 그 위에 기능을 쌓으면 API가 커져도 유지보수 비용이 폭발하지 않습니다.
