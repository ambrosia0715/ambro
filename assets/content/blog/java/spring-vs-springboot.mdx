# 스프링(Spring) vs 스프링 부트(Spring Boot) 비교: 언제 무엇을 써야 할까?

_작성일: 2026-02-09_

신입 개발자 면접에서 "스프링과 스프링 부트의 차이점이 뭔가요?"라는 질문은 단골입니다. "스프링 부트는 스프링의 간편 버전입니다"라고 답하면 절반만 맞는 것입니다. 스프링 부트는 스프링 프레임워크 **위에서** 동작하며, 스프링의 개념을 숨기는 것이 아니라 **합리적인 기본값을 제공해 빠르게 시작할 수 있게** 돕는 도구입니다.

이 글에서는 실제 코드를 비교하며 둘의 차이를 명확히 하고, 실무에서 어떤 상황에 어떤 선택을 해야 하는지 구체적인 가이드를 제공합니다.

![Spring vs Spring Boot 비교](assets/images/blog/spring_vs_boot_hero.webp)

## 1. 한 문장 정의

- **Spring Framework**: 유연하고 확장 가능한 애플리케이션 아키텍처 기반 (IoC/DI, AOP, MVC 등의 레고 블록)
- **Spring Boot**: 그 레고 블록을 빠르게 조립할 수 있는 표준 키트 (자동 설정 + 내장 서버 + Starter)

## 2. 핵심 차이 비교표

| 항목 | Spring Framework | Spring Boot |
|---|---|---|
| 목적 | 유연한 아키텍처 기반 (IoC/DI, AOP) | 빠른 시작 + 합리적 기본값 + 운영 친화 |
| 설정 방식 | XML 또는 Java Config 수동 설정 | Auto Configuration 중심 |
| 의존성 관리 | 필요한 모듈을 개별 조합 | Starter로 기능 단위 묶음 제공 |
| 서버 실행 | 외부 WAS(Tomcat, JBoss) 필요 | 내장 서버로 JAR 실행 |
| 배포 방식 | WAR 패키징 → WAS에 배포 | JAR 패키징 → `java -jar` 실행 |
| 운영 기능 | 별도 구성 필요 | Actuator로 헬스체크/메트릭 제공 |
| 학습 곡선 | 내부 구조 이해 필요 (높음) | 시작은 쉬움, 성장하며 내부 이해 필요 |

## 3. 코드로 보는 차이: 동일한 API를 두 방식으로 만들기

### 3.1 Spring Framework (수동 설정)

```java
// 1. 의존성 — 개별 라이브러리 버전을 직접 관리해야 함
// spring-webmvc:6.1.5
// jackson-databind:2.17.0
// tomcat-embed-core:10.1.19
// ... 버전 충돌 주의

// 2. 설정 클래스 — 직접 작성해야 함
@Configuration
@EnableWebMvc
@ComponentScan("com.example")
public class WebConfig implements WebMvcConfigurer {

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper()
            .registerModule(new JavaTimeModule());
    }

    @Override
    public void configureMessageConverters(List<HttpMessageConverter<?>> converters) {
        converters.add(new MappingJackson2HttpMessageConverter(objectMapper()));
    }
}

// 3. DispatcherServlet 등록 — 직접 해야 함
public class WebInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {
    @Override
    protected Class<?>[] getRootConfigClasses() {
        return new Class[]{AppConfig.class};
    }

    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class[]{WebConfig.class};
    }

    @Override
    protected String[] getServletMappings() {
        return new String[]{"/"};
    }
}

// 4. 컨트롤러 — 이 부분은 동일
@RestController
public class HelloController {
    @GetMapping("/hello")
    public Map<String, String> hello() {
        return Map.of("message", "Hello Spring");
    }
}

// 5. 배포: WAR로 패키징 → 외부 Tomcat에 배포
```

### 3.2 Spring Boot (자동 설정)

```gradle
// 1. 의존성 — Starter 하나로 해결
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
```

```java
// 2. 메인 클래스 — 이것이 전부
@SpringBootApplication
public class MyApp {
    public static void main(String[] args) {
        SpringApplication.run(MyApp.class, args);
    }
}

// 3. 컨트롤러 — 동일
@RestController
public class HelloController {
    @GetMapping("/hello")
    public Map<String, String> hello() {
        return Map.of("message", "Hello Spring Boot");
    }
}

// 4. 배포: ./gradlew bootJar → java -jar app.jar
```

차이가 명확합니다. Spring Framework는 **WebConfig, WebInitializer, ObjectMapper 설정, DispatcherServlet 등록**을 모두 수동으로 해야 합니다. Spring Boot는 `@SpringBootApplication` 하나로 이 모든 것이 자동 설정됩니다.

## 4. Auto Configuration은 어떻게 동작하는가?

스프링 부트의 자동 설정은 "마법"이 아니라 **조건부 빈 등록(@Conditional)**입니다.

```java
// 스프링 부트 내부의 자동 설정 예시 (단순화)
@Configuration
@ConditionalOnClass(DataSource.class) // DataSource가 클래스패스에 있을 때만
@ConditionalOnMissingBean(DataSource.class) // 개발자가 직접 정의하지 않았을 때만
public class DataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource(DataSourceProperties properties) {
        return DataSourceBuilder.create()
            .url(properties.getUrl())
            .username(properties.getUsername())
            .build();
    }
}
```

핵심 원칙: **클래스패스에 라이브러리가 있으면 자동 설정하되, 개발자가 직접 빈을 정의하면 자동 설정은 물러난다.** 따라서 기본값을 쓰다가 필요할 때만 오버라이드하면 됩니다.

자동 설정이 무엇을 했는지 확인하려면 `--debug` 플래그로 실행하세요:

```bash
java -jar app.jar --debug
# 또는 application.yml에 debug: true
```

## 5. 언제 무엇을 선택하는가?

### Spring Boot를 선택하는 경우 (대부분)

- 신규 프로젝트를 빠르게 시작하고 싶을 때
- 팀 전체가 일관된 구성을 사용해야 할 때
- 마이크로서비스/Docker/Kubernetes 환경
- 운영 모니터링(Actuator)이 필요할 때
- REST API 서버를 구축할 때

### Spring Framework를 더 세밀하게 다루는 경우

실무에서는 "Boot를 쓰되, 특정 부분만 커스터마이즈"하는 것이 일반적입니다.

- 사내 공통 프레임워크/라이브러리를 개발할 때
- 자동 설정이 방해가 되는 매우 특수한 환경
- 레거시 WAR 배포가 강제되는 환경 (이 경우도 Boot의 WAR 모드 사용 가능)
- 스프링 배치 등 특수 목적 프레임워크와 깊은 통합이 필요할 때

## 6. 실전 마이그레이션 가이드: Spring → Spring Boot

기존 Spring Framework 프로젝트를 Spring Boot로 전환하는 단계입니다.

```
단계 1: build.gradle에 Spring Boot 플러그인 추가
단계 2: @SpringBootApplication 메인 클래스 생성
단계 3: XML 설정을 Java Config로 변환
단계 4: web.xml 제거 (DispatcherServlet 자동 등록)
단계 5: 외부 Tomcat 의존성 제거 (내장 서버 사용)
단계 6: application.yml로 설정 이관
단계 7: WAR → JAR 패키징 변경
```

**팁**: 한 번에 전부 전환하지 마세요. Boot는 WAR 패키징도 지원하므로, 먼저 Boot 기반으로 전환한 뒤 점진적으로 JAR로 전환하는 것이 안전합니다.

## 7. 흔한 오해 바로잡기

**오해 1: "스프링 부트는 스프링과 다른 프레임워크다"**

아닙니다. 스프링 부트 = 스프링 프레임워크 + 자동 설정 + 운영 도구입니다. 내부적으로 동일한 IoC/DI, AOP, MVC가 동작합니다.

**오해 2: "스프링 부트를 쓰면 스프링을 몰라도 된다"**

처음에는 그렇게 느낄 수 있지만, 문제가 발생하면 결국 스프링의 내부 동작을 이해해야 합니다. `@Transactional`이 왜 안 먹히는지, 빈이 왜 주입되지 않는지 디버깅하려면 IoC 컨테이너를 알아야 합니다.

**오해 3: "스프링 부트는 가볍다"**

스프링 부트는 빠르게 시작할 수 있지만, 결과물이 "가벼운" 것은 아닙니다. Auto Configuration이 불필요한 빈도 등록할 수 있으므로, 프로덕션에서는 `spring.autoconfigure.exclude`로 불필요한 설정을 제외하는 것이 좋습니다.

```yaml
spring:
  autoconfigure:
    exclude:
      - org.springframework.boot.autoconfigure.mail.MailSenderAutoConfiguration
      - org.springframework.boot.autoconfigure.data.redis.RedisAutoConfiguration
```

## 결론: 실무 선택 기준

| 기준 | 추천 |
|---|---|
| 새 프로젝트 | Spring Boot |
| 빠른 프로토타이핑 | Spring Boot |
| 사내 플랫폼 레벨 모듈 | Spring Framework 직접 활용 |
| 레거시 마이그레이션 | Spring Boot (점진적 전환) |

최선의 전략은 **"부트로 시작하고, 성장하면서 스프링의 내부를 이해해 커스터마이즈하는 것"**입니다. 부트는 스프링을 숨기는 도구가 아니라, 현실적인 기본값을 제공해 팀이 더 빨리 제품을 만들도록 돕는 도구입니다.
