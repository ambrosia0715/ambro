# 스프링(Spring) vs 스프링 부트(Spring Boot) 비교: 언제 무엇을 써야 할까?

_작성일: 2026-02-09_

스프링과 스프링 부트는 “서로 경쟁하는 제품”이 아닙니다. 스프링 부트는 스프링 프레임워크 위에서 동작하며, 스프링을 더 빠르고 안전하게 시작하도록 돕습니다. 그럼에도 실무에서는 “둘의 차이”를 명확히 알고 선택 기준을 세우는 것이 중요합니다. 이 글에서는 개념/구조/사용 방식 관점에서 비교하고, 실제 선택 가이드를 정리합니다.

![Spring vs Spring Boot 비교](assets/images/blog/spring_vs_boot_hero.webp)

## 1) 한 문장으로 요약

- **Spring**: 유연하고 확장 가능한 “프레임워크 구성 요소(레고)”  
- **Spring Boot**: 그 레고를 빠르게 조립할 수 있게 해주는 “표준 조립 키트”  

## 2) 무엇이 달라지는가? (비교 표)

| 항목 | Spring Framework | Spring Boot |
|---|---|---|
| 목적 | 유연한 아키텍처 기반 제공(IoC/DI, AOP 등) | 빠른 시작 + 합리적 기본값 + 운영 친화 |
| 설정 방식 | 선택지가 많고 수동 설정이 많을 수 있음 | 자동 설정(Auto Config) 중심 |
| 의존성 관리 | 필요한 모듈을 직접 조합 | Starter로 기능 단위 의존성 묶음 제공 |
| 서버/실행 | 외부 WAS 설정이 필요할 수 있음 | 내장 서버(Embedded)로 바로 실행 |
| 운영 기능 | 별도 구성 필요 | Actuator 등 운영 기능을 쉽게 추가 |
| 학습 난이도 | 구조 이해가 필요(상대적으로 높음) | 시작은 쉬움(성장하며 내부 이해 필요) |

## 3) 구조 관점 비교

### Spring Framework

- “컨테이너(ApplicationContext)”가 Bean을 생성/조립
- AOP로 공통 관심사를 분리
- MVC/Data 등 모듈을 선택적으로 조합

### Spring Boot

- `@SpringBootApplication` 진입점 + 자동설정이 중심
- 클래스패스와 설정 파일을 기반으로 조건부 Bean 등록
- 표준 폴더/설정 규약을 제공해 팀 합의를 단순화

결국 부트는 **스프링을 더 ‘표준화된 방식으로’ 쓰게** 만들어, 초기 생산성과 운영 일관성을 높입니다.

## 4) 언제 Spring을 “직접” 쓰고, 언제 Boot를 쓰나?

### Spring Boot를 추천하는 경우(대부분)

- 신규 서비스/프로덕션 API 서버
- 팀 개발에서 표준이 필요할 때
- 빠른 PoC → 점진적 확장
- 운영(헬스체크/메트릭/로그)까지 고려해야 할 때

### Spring을 더 세밀하게 제어해야 하는 경우

실제로는 “Boot를 쓰되 설정을 커스터마이즈”하는 편이 더 일반적입니다. 그럼에도 아래처럼 아주 특수한 요구가 있으면 스프링 구성 요소를 더 직접적으로 다루게 됩니다.

- 사내 플랫폼/프레임워크 레벨의 공통 모듈을 만드는 경우
- 자동설정이 오히려 방해가 되는 매우 특수한 런타임/환경
- 오래된 레거시 시스템과의 강한 결합(점진적 마이그레이션)

## 5) 선택 가이드: 실무 기준 체크리스트

- **시간이 중요하면**: Boot로 시작  
- **표준/일관성이 중요하면**: Boot(Starter/Auto Config/규약)  
- **아키텍처 자유도가 최우선이면**: Boot를 쓰되, 내부 Spring 구조를 이해하고 필요한 부분을 오버라이드  

## 결론

스프링 부트는 스프링의 개념과 구조를 “숨기는” 도구가 아니라, **현실적인 기본값을 제공해 팀이 더 빨리 제품을 만들도록 돕는 도구**입니다. 최선의 선택은 보통 “부트로 시작하고, 성장하면서 스프링의 구조를 이해해 커스터마이즈하는 것”입니다.
