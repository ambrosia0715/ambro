    <article><h1>스프링(Spring) vs 스프링 부트(Spring Boot) 비교: 언제 무엇을 써야 할까?</h1>
<p><em>작성일: 2026-02-09</em></p>
<p>신입 개발자 면접에서 "스프링과 스프링 부트의 차이점이 뭔가요?"라는 질문은 단골입니다. "스프링 부트는 스프링의 간편 버전입니다"라고 답하면 절반만 맞는 것입니다. 스프링 부트는 스프링 프레임워크 <strong>위에서</strong> 동작하며, 스프링의 개념을 숨기는 것이 아니라 <strong>합리적인 기본값을 제공해 빠르게 시작할 수 있게</strong> 돕는 도구입니다.</p>
<p>이 글에서는 실제 코드를 비교하며 둘의 차이를 명확히 하고, 실무에서 어떤 상황에 어떤 선택을 해야 하는지 구체적인 가이드를 제공합니다.</p>
<img src="/assets/assets/images/blog/spring_vs_boot_hero.webp" alt="Spring vs Spring Boot 비교" loading="lazy" style="max-width:100%;height:auto;border-radius:8px;margin:1em 0;">
<h2>1. 한 문장 정의</h2>
<ul>
<li><strong>Spring Framework</strong>: 유연하고 확장 가능한 애플리케이션 아키텍처 기반 (IoC/DI, AOP, MVC 등의 레고 블록)</li>
<li><strong>Spring Boot</strong>: 그 레고 블록을 빠르게 조립할 수 있는 표준 키트 (자동 설정 + 내장 서버 + Starter)</li>
</ul>
<h2>2. 핵심 차이 비교표</h2>
<table><thead><tr>
<th>항목</th>
<th>Spring Framework</th>
<th>Spring Boot</th>
</tr></thead><tbody>
<tr>
<td>목적</td>
<td>유연한 아키텍처 기반 (IoC/DI, AOP)</td>
<td>빠른 시작 + 합리적 기본값 + 운영 친화</td>
</tr>
<tr>
<td>설정 방식</td>
<td>XML 또는 Java Config 수동 설정</td>
<td>Auto Configuration 중심</td>
</tr>
<tr>
<td>의존성 관리</td>
<td>필요한 모듈을 개별 조합</td>
<td>Starter로 기능 단위 묶음 제공</td>
</tr>
<tr>
<td>서버 실행</td>
<td>외부 WAS(Tomcat, JBoss) 필요</td>
<td>내장 서버로 JAR 실행</td>
</tr>
<tr>
<td>배포 방식</td>
<td>WAR 패키징 → WAS에 배포</td>

</tr>
<tr>
<td>운영 기능</td>
<td>별도 구성 필요</td>

</tr>
<tr>
<td>학습 곡선</td>
<td>내부 구조 이해 필요 (높음)</td>
<td>시작은 쉬움, 성장하며 내부 이해 필요</td>
</tr>
</tbody></table>
<h2>3. 코드로 보는 차이: 동일한 API를 두 방식으로 만들기</h2>
<h3>3.1 Spring Framework (수동 설정)</h3>
<pre><code class="language-java">
// 1. 의존성 — 개별 라이브러리 버전을 직접 관리해야 함
// spring-webmvc:6.1.5
// jackson-databind:2.17.0
// tomcat-embed-core:10.1.19
// ... 버전 충돌 주의

// 2. 설정 클래스 — 직접 작성해야 함
@Configuration
@EnableWebMvc
@ComponentScan("com.example")
public class WebConfig implements WebMvcConfigurer {

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper()
            .registerModule(new JavaTimeModule());
    }

    @Override
    public void configureMessageConverters(List&lt;HttpMessageConverter&lt;?&gt;&gt; converters) {
        converters.add(new MappingJackson2HttpMessageConverter(objectMapper()));
    }
}

// 3. DispatcherServlet 등록 — 직접 해야 함
public class WebInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {
    @Override
    protected Class&lt;?&gt;[] getRootConfigClasses() {
        return new Class[]{AppConfig.class};
    }

    @Override
    protected Class&lt;?&gt;[] getServletConfigClasses() {
        return new Class[]{WebConfig.class};
    }

    @Override
    protected String[] getServletMappings() {
        return new String[]{"/"};
    }
}

// 4. 컨트롤러 — 이 부분은 동일
@RestController
public class HelloController {
    @GetMapping("/hello")
    public Map&lt;String, String&gt; hello() {
        return Map.of("message", "Hello Spring");
    }
}

// 5. 배포: WAR로 패키징 → 외부 Tomcat에 배포
</code></pre>
<h3>3.2 Spring Boot (자동 설정)</h3>
<pre><code class="language-gradle">
// 1. 의존성 — Starter 하나로 해결
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
</code></pre>
<pre><code class="language-java">
// 2. 메인 클래스 — 이것이 전부
@SpringBootApplication
public class MyApp {
    public static void main(String[] args) {
        SpringApplication.run(MyApp.class, args);
    }
}

// 3. 컨트롤러 — 동일
@RestController
public class HelloController {
    @GetMapping("/hello")
    public Map&lt;String, String&gt; hello() {
        return Map.of("message", "Hello Spring Boot");
    }
}

// 4. 배포: ./gradlew bootJar → java -jar app.jar
</code></pre>
<p>차이가 명확합니다. Spring Framework는 <strong>WebConfig, WebInitializer, ObjectMapper 설정, DispatcherServlet 등록</strong>을 모두 수동으로 해야 합니다. Spring Boot는 <code>@SpringBootApplication</code> 하나로 이 모든 것이 자동 설정됩니다.</p>
<h2>4. Auto Configuration은 어떻게 동작하는가?</h2>
<p>스프링 부트의 자동 설정은 "마법"이 아니라 <strong>조건부 빈 등록(@Conditional)</strong>입니다.</p>
<pre><code class="language-java">
// 스프링 부트 내부의 자동 설정 예시 (단순화)
@Configuration
@ConditionalOnClass(DataSource.class) // DataSource가 클래스패스에 있을 때만
@ConditionalOnMissingBean(DataSource.class) // 개발자가 직접 정의하지 않았을 때만
public class DataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource(DataSourceProperties properties) {
        return DataSourceBuilder.create()
            .url(properties.getUrl())
            .username(properties.getUsername())
            .build();
    }
}
</code></pre>
<p>핵심 원칙: <strong>클래스패스에 라이브러리가 있으면 자동 설정하되, 개발자가 직접 빈을 정의하면 자동 설정은 물러난다.</strong> 따라서 기본값을 쓰다가 필요할 때만 오버라이드하면 됩니다.</p>
<p>자동 설정이 무엇을 했는지 확인하려면 <code>--debug</code> 플래그로 실행하세요:</p>
<pre><code class="language-bash">
java -jar app.jar --debug
# 또는 application.yml에 debug: true
</code></pre>
<h2>5. 언제 무엇을 선택하는가?</h2>
<h3>Spring Boot를 선택하는 경우 (대부분)</h3>
<ul>
<li>신규 프로젝트를 빠르게 시작하고 싶을 때</li>
<li>팀 전체가 일관된 구성을 사용해야 할 때</li>
<li>마이크로서비스/Docker/Kubernetes 환경</li>
<li>운영 모니터링(Actuator)이 필요할 때</li>
<li>REST API 서버를 구축할 때</li>
</ul>
<h3>Spring Framework를 더 세밀하게 다루는 경우</h3>
<p>실무에서는 "Boot를 쓰되, 특정 부분만 커스터마이즈"하는 것이 일반적입니다.</p>
<ul>
<li>사내 공통 프레임워크/라이브러리를 개발할 때</li>
<li>자동 설정이 방해가 되는 매우 특수한 환경</li>
<li>레거시 WAR 배포가 강제되는 환경 (이 경우도 Boot의 WAR 모드 사용 가능)</li>
<li>스프링 배치 등 특수 목적 프레임워크와 깊은 통합이 필요할 때</li>
</ul>
<h2>6. 실전 마이그레이션 가이드: Spring → Spring Boot</h2>
<p>기존 Spring Framework 프로젝트를 Spring Boot로 전환하는 단계입니다.</p>
<pre><code class="language-">
단계 1: build.gradle에 Spring Boot 플러그인 추가
단계 2: @SpringBootApplication 메인 클래스 생성
단계 3: XML 설정을 Java Config로 변환
단계 4: web.xml 제거 (DispatcherServlet 자동 등록)
단계 5: 외부 Tomcat 의존성 제거 (내장 서버 사용)
단계 6: application.yml로 설정 이관
단계 7: WAR → JAR 패키징 변경
</code></pre>
<p><strong>팁</strong>: 한 번에 전부 전환하지 마세요. Boot는 WAR 패키징도 지원하므로, 먼저 Boot 기반으로 전환한 뒤 점진적으로 JAR로 전환하는 것이 안전합니다.</p>
<h2>7. 흔한 오해 바로잡기</h2>
<p><strong>오해 1: "스프링 부트는 스프링과 다른 프레임워크다"</strong></p>
<p>아닙니다. 스프링 부트 = 스프링 프레임워크 + 자동 설정 + 운영 도구입니다. 내부적으로 동일한 IoC/DI, AOP, MVC가 동작합니다.</p>
<p><strong>오해 2: "스프링 부트를 쓰면 스프링을 몰라도 된다"</strong></p>
<p>처음에는 그렇게 느낄 수 있지만, 문제가 발생하면 결국 스프링의 내부 동작을 이해해야 합니다. <code>@Transactional</code>이 왜 안 먹히는지, 빈이 왜 주입되지 않는지 디버깅하려면 IoC 컨테이너를 알아야 합니다.</p>
<p><strong>오해 3: "스프링 부트는 가볍다"</strong></p>
<p>스프링 부트는 빠르게 시작할 수 있지만, 결과물이 "가벼운" 것은 아닙니다. Auto Configuration이 불필요한 빈도 등록할 수 있으므로, 프로덕션에서는 <code>spring.autoconfigure.exclude</code>로 불필요한 설정을 제외하는 것이 좋습니다.</p>
<pre><code class="language-yaml">
spring:
  autoconfigure:
    exclude:
      - org.springframework.boot.autoconfigure.mail.MailSenderAutoConfiguration
      - org.springframework.boot.autoconfigure.data.redis.RedisAutoConfiguration
</code></pre>
<h2>결론: 실무 선택 기준</h2>
<table><thead><tr>
<th>기준</th>
<th>추천</th>
</tr></thead><tbody>
<tr>
<td>새 프로젝트</td>
<td>Spring Boot</td>
</tr>
<tr>
<td>빠른 프로토타이핑</td>
<td>Spring Boot</td>
</tr>
<tr>
<td>사내 플랫폼 레벨 모듈</td>
<td>Spring Framework 직접 활용</td>
</tr>
<tr>
<td>레거시 마이그레이션</td>
<td>Spring Boot (점진적 전환)</td>
</tr>
</tbody></table>
<p>최선의 전략은 <strong>"부트로 시작하고, 성장하면서 스프링의 내부를 이해해 커스터마이즈하는 것"</strong>입니다. 부트는 스프링을 숨기는 도구가 아니라, 현실적인 기본값을 제공해 팀이 더 빨리 제품을 만들도록 돕는 도구입니다.</p></article>
