    <article><h1>스프링(Spring) vs 스프링 부트(Spring Boot) 비교: 언제 무엇을 써야 할까?</h1>
<p><em>작성일: 2026-02-09</em></p>
<p>스프링과 스프링 부트는 “서로 경쟁하는 제품”이 아닙니다. 스프링 부트는 스프링 프레임워크 위에서 동작하며, 스프링을 더 빠르고 안전하게 시작하도록 돕습니다. 그럼에도 실무에서는 “둘의 차이”를 명확히 알고 선택 기준을 세우는 것이 중요합니다. 이 글에서는 개념/구조/사용 방식 관점에서 비교하고, 실제 선택 가이드를 정리합니다.</p>
<img src="/assets/assets/images/blog/spring_vs_boot_hero.webp" alt="Spring vs Spring Boot 비교" loading="lazy" style="max-width:100%;height:auto;border-radius:8px;margin:1em 0;">
<h2>1) 한 문장으로 요약</h2>
<ul>
<li><strong>Spring</strong>: 유연하고 확장 가능한 “프레임워크 구성 요소(레고)”</li>
<li><strong>Spring Boot</strong>: 그 레고를 빠르게 조립할 수 있게 해주는 “표준 조립 키트”</li>
</ul>
<h2>2) 무엇이 달라지는가? (비교 표)</h2>
<table><thead><tr>
<th>항목</th>
<th>Spring Framework</th>
<th>Spring Boot</th>
</tr></thead><tbody>
<tr>
<td>목적</td>
<td>유연한 아키텍처 기반 제공(IoC/DI, AOP 등)</td>
<td>빠른 시작 + 합리적 기본값 + 운영 친화</td>
</tr>
<tr>
<td>설정 방식</td>
<td>선택지가 많고 수동 설정이 많을 수 있음</td>
<td>자동 설정(Auto Config) 중심</td>
</tr>
<tr>
<td>의존성 관리</td>
<td>필요한 모듈을 직접 조합</td>
<td>Starter로 기능 단위 의존성 묶음 제공</td>
</tr>
<tr>
<td>서버/실행</td>
<td>외부 WAS 설정이 필요할 수 있음</td>
<td>내장 서버(Embedded)로 바로 실행</td>
</tr>
<tr>
<td>운영 기능</td>
<td>별도 구성 필요</td>
<td>Actuator 등 운영 기능을 쉽게 추가</td>
</tr>
<tr>
<td>학습 난이도</td>
<td>구조 이해가 필요(상대적으로 높음)</td>
<td>시작은 쉬움(성장하며 내부 이해 필요)</td>
</tr>
</tbody></table>
<h2>3) 구조 관점 비교</h2>
<h3>Spring Framework</h3>
<ul>
<li>“컨테이너(ApplicationContext)”가 Bean을 생성/조립</li>
<li>AOP로 공통 관심사를 분리</li>
<li>MVC/Data 등 모듈을 선택적으로 조합</li>
</ul>
<h3>Spring Boot</h3>
<ul>
<li><code>@SpringBootApplication</code> 진입점 + 자동설정이 중심</li>
<li>클래스패스와 설정 파일을 기반으로 조건부 Bean 등록</li>
<li>표준 폴더/설정 규약을 제공해 팀 합의를 단순화</li>
</ul>
<p>결국 부트는 <strong>스프링을 더 ‘표준화된 방식으로’ 쓰게</strong> 만들어, 초기 생산성과 운영 일관성을 높입니다.</p>
<h2>4) 언제 Spring을 “직접” 쓰고, 언제 Boot를 쓰나?</h2>
<h3>Spring Boot를 추천하는 경우(대부분)</h3>
<ul>
<li>신규 서비스/프로덕션 API 서버</li>
<li>팀 개발에서 표준이 필요할 때</li>
<li>빠른 PoC → 점진적 확장</li>
<li>운영(헬스체크/메트릭/로그)까지 고려해야 할 때</li>
</ul>
<h3>Spring을 더 세밀하게 제어해야 하는 경우</h3>
<p>실제로는 “Boot를 쓰되 설정을 커스터마이즈”하는 편이 더 일반적입니다. 그럼에도 아래처럼 아주 특수한 요구가 있으면 스프링 구성 요소를 더 직접적으로 다루게 됩니다.</p>
<ul>
<li>사내 플랫폼/프레임워크 레벨의 공통 모듈을 만드는 경우</li>
<li>자동설정이 오히려 방해가 되는 매우 특수한 런타임/환경</li>
<li>오래된 레거시 시스템과의 강한 결합(점진적 마이그레이션)</li>
</ul>
<h2>5) 선택 가이드: 실무 기준 체크리스트</h2>
<ul>
<li><strong>시간이 중요하면</strong>: Boot로 시작</li>
<li><strong>표준/일관성이 중요하면</strong>: Boot(Starter/Auto Config/규약)</li>
<li><strong>아키텍처 자유도가 최우선이면</strong>: Boot를 쓰되, 내부 Spring 구조를 이해하고 필요한 부분을 오버라이드</li>
</ul>
<h2>결론</h2>
<p>스프링 부트는 스프링의 개념과 구조를 “숨기는” 도구가 아니라, <strong>현실적인 기본값을 제공해 팀이 더 빨리 제품을 만들도록 돕는 도구</strong>입니다. 최선의 선택은 보통 “부트로 시작하고, 성장하면서 스프링의 구조를 이해해 커스터마이즈하는 것”입니다.</p></article>
