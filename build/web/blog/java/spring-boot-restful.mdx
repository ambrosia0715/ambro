    <h1>Spring Boot RESTful 사용방법: 설정과 작성 패턴</h1>
    <div class="meta">2026-02-09 &middot; 9분 &middot; Ambro</div>
    <img src="/assets/assets/images/blog/spring_boot_rest.webp" alt="Spring Boot RESTful 사용방법: 설정과 작성 패턴" style="width:100%;border-radius:12px;margin-bottom:2em;">
    <article><h1>Spring Boot에서 RESTful API 만들기: 설정부터 작성 패턴까지</h1>
<p><em>작성일: 2026-02-09</em></p>
<p>RESTful API는 <strong>URL로 자원(Resource)</strong>, <strong>HTTP 메서드로 행위(Action)</strong>를 표현해 일관된 인터페이스를 만드는 방식입니다. Spring Boot는 REST에 필요한 구성(Jackson, 내장 서버, MVC)을 기본값으로 제공해 빠르게 시작할 수 있습니다. 이 글에서는 Boot 환경에서 REST API를 만들 때 필요한 <strong>설정(의존성/JSON/검증/예외 처리)</strong>과 <strong>메서드별 URL 양식</strong>, 그리고 실무에서 자주 헷갈리는 포인트(PUT vs PATCH, 여러 ID/필터 처리)를 예시와 함께 정리합니다.</p>
<img src="/assets/assets/images/blog/spring_boot_rest.webp" alt="Spring Boot REST API" loading="lazy" style="max-width:100%;height:auto;border-radius:8px;margin:1em 0;">
<h2>1) 기본 설정: 의존성과 프로젝트 준비</h2>
<p>Spring Boot에서 REST API를 만들 때 가장 기본은 <code>spring-boot-starter-web</code>입니다.</p>
<pre><code class="language-gradle">
dependencies {
  implementation 'org.springframework.boot:spring-boot-starter-web'
  implementation 'org.springframework.boot:spring-boot-starter-validation'
  testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
</code></pre>
<ul>
<li><code>starter-web</code>: <code>@RestController</code>, Jackson(JSON), 내장 톰캣 등 REST에 필요한 기본 묶음</li>
<li><code>starter-validation</code>: <code>@Valid</code>로 요청 DTO 검증(Bean Validation)</li>
</ul>
<h3>(추가) 기본 설정 파일 예시</h3>
<p>요청/응답 로깅이나 JSON 네이밍 같은 “팀 기본값”은 <code>application.yml</code>로 통일하는 게 좋습니다.</p>
<pre><code class="language-yaml">
server:
  port: 8080

spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
</code></pre>
<h2>2) 작성 패턴(핵심만)</h2>
<ul>
<li><strong>Controller는 얇게</strong>: HTTP 입출력만 처리하고, 규칙은 Service로</li>
<li><strong>DTO 분리</strong>: 엔티티 노출 대신 Request/Response DTO로 계약 고정</li>
<li><strong>검증</strong>: <code>@Valid</code> + <code>starter-validation</code>으로 요청값을 초기에 차단</li>
</ul>
<p>간단한 계층 예시는 아래처럼 생각하면 됩니다.</p>
<pre><code class="language-text">
Controller(HTTP) → Service(규칙/트랜잭션) → Repository(DB)
</code></pre>
<h2>3) RESTful하게 설계하는 규칙(실무 체크리스트)</h2>
<h3>(1) URL은 자원 중심으로</h3>
<ul>
<li>좋은 예: <code>GET /users/1</code>, <code>POST /users</code>, <code>PUT /users/1</code></li>
<li>덜 좋은 예: <code>POST /createUser</code>, <code>GET /getUser</code></li>
</ul>
<h3>(2) 메서드별 선언 & URL 양식(예시)</h3>
<p>REST는 보통 “목록 URL”과 “단건 URL”을 나눕니다.</p>
<table><thead><tr>
<th>메서드</th>
<th>URL 양식</th>
<th>의미</th>
<th>Spring Boot 선언</th>
<th>파라미터 받기(예시)</th>
</tr></thead><tbody>
<tr>
<td>GET</td>
<td><code>/api/v1/users</code></td>
<td>목록 조회(페이징/필터)</td>
<td><code>@GetMapping</code></td>
<td><code>@RequestParam int page, int size</code> / 여러 값: <code>@RequestParam List<Long> ids</code></td>
</tr>
<tr>
<td>GET</td>
<td><code>/api/v1/users/{id}</code></td>
<td>단건 조회</td>
<td><code>@GetMapping("/{id}")</code></td>
<td><code>@PathVariable Long id</code></td>
</tr>
<tr>
<td>POST</td>
<td><code>/api/v1/users</code></td>
<td>생성</td>
<td><code>@PostMapping</code></td>
<td><code>@RequestBody CreateUserRequest body</code></td>
</tr>
<tr>
<td>PUT</td>
<td><code>/api/v1/users/{id}</code></td>
<td>전체 교체(멱등)</td>
<td><code>@PutMapping("/{id}")</code></td>
<td><code>@PathVariable Long id, @RequestBody UpdateUserRequest body</code></td>
</tr>
<tr>
<td>PATCH</td>
<td><code>/api/v1/users/{id}</code></td>
<td>부분 수정</td>
<td><code>@PatchMapping("/{id}")</code></td>
<td><code>@PathVariable Long id, @RequestBody PatchUserRequest body</code></td>
</tr>
<tr>
<td>DELETE</td>
<td><code>/api/v1/users/{id}</code></td>
<td>삭제(멱등)</td>
<td><code>@DeleteMapping("/{id}")</code></td>
<td><code>@PathVariable Long id</code></td>
</tr>
</tbody></table>
<h4><code>id</code> 값을 실제로 “받아서 쓰는” 방법</h4>
<pre><code class="language-java">
@GetMapping("/{id}")
public UserResponse get(@PathVariable Long id) {
  return userService.getById(id);
}
</code></pre>
<h4>값을 여러 개 받을 때(대표 패턴 2가지)</h4>
<ul>
<li><strong>PathVariable 여러 개</strong>: 리소스가 계층 구조일 때</li>
</ul>
<pre><code class="language-java">
@GetMapping("/users/{userId}/orders/{orderId}")
public OrderResponse getOrder(
  @PathVariable Long userId,
  @PathVariable Long orderId
) { /* ... */ }
</code></pre>
<ul>
<li><strong>QueryParam 여러 개</strong>: 필터/검색/배치 조회일 때</li>
</ul>
<pre><code class="language-java">
@GetMapping
public List&lt;UserResponse&gt; list(@RequestParam List&lt;Long&gt; ids) { /* ... */ }
// 호출 예: /api/v1/users?ids=1&amp;ids=2&amp;ids=3
</code></pre>
<blockquote><p>팁: “여러 ID로 조회”가 핵심 요구라면 <code>/users:batchGet</code> 같은 RPC 스타일 대신, 위처럼 QueryParam으로 해결하면 REST 스타일을 유지하기 쉽습니다.</p></blockquote>
<blockquote><p>참고: 사용자가 “push”라고 말하는 경우가 있는데, REST 표준 HTTP 메서드는 <strong>POST</strong>입니다.</p></blockquote>
<h3>(3) 상태코드를 명확히</h3>
<ul>
<li>생성 성공: <code>201 Created</code></li>
<li>잘못된 요청: <code>400 Bad Request</code></li>
<li>리소스 없음: <code>404 Not Found</code></li>
</ul>
<p>Spring에서는 <code>ResponseEntity</code>로 상태코드와 헤더를 명시할 수 있습니다.</p>
<h4><code>POST</code>에서 Location 헤더 주기(권장)</h4>
<pre><code class="language-java">
@PostMapping
public ResponseEntity&lt;UserResponse&gt; create(@Valid @RequestBody CreateUserRequest req) {
  var created = userService.create(req);
  return ResponseEntity
    .created(URI.create("/api/v1/users/" + created.id()))
    .body(created);
}
</code></pre>
<h3>(4) PUT vs PATCH, 언제 쓰나?</h3>
<ul>
<li><strong>PUT</strong>: 리소스를 “전체 교체”하는 의미. 같은 요청을 여러 번 보내도 결과가 같아야(멱등) 합니다.</li>
<li><strong>PATCH</strong>: 일부 필드만 변경. 변경 필드가 많지 않거나 부분 업데이트가 잦을 때 유리합니다.</li>
</ul>
<p>실무에서는 “사용자 프로필 전체 수정” 같은 화면은 PUT, “알림 설정 한 개 토글” 같은 화면은 PATCH로 구분하는 편이 자연스럽습니다.</p>
<h2>4) 예외 처리: API 품질을 좌우하는 핵심</h2>
<p>REST API는 실패했을 때도 “읽기 쉬운 규격화된 응답”을 주는 것이 중요합니다. Spring Boot에서는 <code>@RestControllerAdvice</code>로 전역 예외 처리를 구성합니다.</p>
<pre><code class="language-java">
@RestControllerAdvice
public class GlobalExceptionHandler {
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public ResponseEntity&lt;ErrorResponse&gt; handleValidation(MethodArgumentNotValidException e) {
    return ResponseEntity.badRequest().body(ErrorResponse.of("VALIDATION_ERROR", "요청값이 올바르지 않습니다."));
  }
}

public record ErrorResponse(String code, String message) {
  static ErrorResponse of(String code, String message) { return new ErrorResponse(code, message); }
}
</code></pre>
<p>검증 오류(400)가 발생했을 때, 프론트가 메시지를 바로 표시할 수 있도록 <code>code/message</code> 구조를 통일해두면 운영이 편해집니다.</p>
<h2>5) 실전 팁(최소 세트)</h2>
<ul>
<li><strong>버전</strong>: <code>/api/v1</code> 등 규칙을 초기에 고정</li>
<li><strong>페이징</strong>: 목록 API는 <code>page/size/sort</code> 표준화</li>
</ul>
<p>예를 들어 목록 API는 아래처럼 “기본값”을 두고 확장합니다.</p>
<pre><code class="language-java">
@GetMapping
public Page&lt;UserResponse&gt; list(
  @RequestParam(defaultValue = "0") int page,
  @RequestParam(defaultValue = "20") int size,
  @RequestParam(required = false) String q
) { /* ... */ }
</code></pre>
<h2>결론</h2>
<p>Spring Boot REST API의 핵심은 <strong>규칙과 구조(계층 분리, DTO, 예외 처리)</strong>입니다. URL/메서드 규칙과 오류 응답 포맷을 먼저 고정하고, 그 위에 기능을 쌓으면 API가 커져도 유지보수 비용이 폭발하지 않습니다.</p></article>
