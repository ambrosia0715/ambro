    <article><h1>Spring Boot에서 RESTful API 만들기: 설정부터 작성 패턴까지</h1>
<p><em>작성일: 2026-02-09</em></p>
<p>회사에서 "사용자 관리 API를 만들어주세요"라는 요청을 받았습니다. URL은 어떻게 설계하지? POST와 PUT의 차이는? 에러 응답 형식은? 이런 질문에 대한 답을 모르면 프론트엔드 팀과 소통이 어렵고 유지보수도 힘들어집니다.</p>
<p>이 글에서는 Spring Boot에서 RESTful API를 만들 때 필요한 URL 설계 규칙, DTO 분리, 검증, 예외 처리를 코드와 함께 정리합니다.</p>
<img src="/assets/assets/images/blog/spring_boot_rest.webp" alt="Spring Boot REST API" loading="lazy" style="max-width:100%;height:auto;border-radius:8px;margin:1em 0;">
<h2>1. 프로젝트 설정</h2>
<pre><code class="language-gradle">
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
</code></pre>
<pre><code class="language-yaml">
server:
  port: 8080

spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
    default-property-inclusion: NON_NULL
    serialization:
      write-dates-as-timestamps: false
</code></pre>
<p>JSON 네이밍 전략과 날짜 형식은 프로젝트 초기에 팀 전체가 합의해야 합니다. 나중에 변경하면 프론트엔드 코드가 전부 깨집니다.</p>
<h2>2. 계층 구조와 DTO 분리</h2>
<pre><code class="language-">
Controller: HTTP 입출력 (요청 파싱, 응답 변환, 상태 코드) → 얇게 유지
Service: 비즈니스 규칙, 트랜잭션 관리 → 핵심 로직
Repository: 데이터 접근 (JPA 등)
</code></pre>
<p>엔티티를 직접 응답으로 노출하면 DB 스키마 변경이 API 스펙 변경이 됩니다. 요청/응답 DTO를 반드시 분리하세요.</p>
<pre><code class="language-java">
public record CreateUserRequest(
    @NotBlank(message = "이름은 필수입니다")
    @Size(min = 2, max = 50)
    String name,

    @Email(message = "유효한 이메일을 입력하세요")
    @NotBlank String email,

    @Min(value = 1) int age
) {}

public record UserResponse(Long id, String name, String email, LocalDateTime createdAt) {
    public static UserResponse from(User user) {
        return new UserResponse(user.getId(), user.getName(),
            user.getEmail(), user.getCreatedAt());
    }
}
</code></pre>
<h2>3. RESTful URL 설계 규칙</h2>
<p>URL은 <strong>자원(Resource)</strong>을 나타내고, HTTP 메서드가 <strong>행위(Action)</strong>를 나타냅니다.</p>
<table><thead><tr>
<th>메서드</th>
<th>URL</th>

<tr>

<td><code>/api/v1/users</code></td>
<td>목록 조회</td>
<td><code>@GetMapping</code></td>
</tr>
<tr>
<td>GET</td>

</tr>
<tr>

<td><code>/api/v1/users</code></td>
<td>생성</td>
<td><code>@PostMapping</code></td>
</tr>
<tr>
<td>PUT</td>
<td><code>/api/v1/users/{id}</code></td>
<td>전체 수정 (멱등)</td>
<td><code>@PutMapping("/{id}")</code></td>
</tr>
<tr>
<td>PATCH</td>
<td><code>/api/v1/users/{id}</code></td>

</tr>
</tbody></table>
<p>나쁜 예: <code>POST /createUser</code>, <code>GET /getUserById</code> — 행위를 URL에 넣지 마세요.</p>
<h2>4. 전체 Controller 구현</h2>
<pre><code class="language-java">
@RestController
@RequestMapping("/api/v1/users")
@RequiredArgsConstructor
public class UserController {
    private final UserService userService;

    @GetMapping
    public Page&lt;UserResponse&gt; list(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size,
        @RequestParam(required = false) String query
    ) {
        return userService.findAll(page, size, query);
    }

    @GetMapping("/{id}")
    public UserResponse get(@PathVariable Long id) {
        return userService.getById(id);
    }

    @PostMapping
    public ResponseEntity&lt;UserResponse&gt; create(@Valid @RequestBody CreateUserRequest request) {
        UserResponse created = userService.create(request);
        URI location = URI.create("/api/v1/users/" + created.id());
        return ResponseEntity.created(location).body(created);
    }

    @PutMapping("/{id}")
    public UserResponse update(@PathVariable Long id,
                               @Valid @RequestBody UpdateUserRequest request) {
        return userService.update(id, request);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity&lt;Void&gt; delete(@PathVariable Long id) {
        userService.delete(id);
        return ResponseEntity.noContent().build();
    }
}
</code></pre>
<h3>계층 구조 리소스와 다중 파라미터</h3>

// 다중 ID 배치 조회

<h2>5. PUT vs PATCH — 실무 선택 기준</h2>
<ul>
<li><strong>PUT</strong>: 리소스 전체 교체. 모든 필드가 필수. 같은 요청을 여러 번 보내도 결과 동일(멱등).</li>
<li><strong>PATCH</strong>: 부분 수정. 보낸 필드만 업데이트.</li>
</ul>
<pre><code class="language-java">
// PATCH 구현: null이 아닌 필드만 업데이트
public UserResponse patch(Long id, PatchUserRequest request) {
    User user = userRepository.findById(id)
        .orElseThrow(() -&gt; new UserNotFoundException(id));

    if (request.name() != null) user.updateName(request.name());
    if (request.email() != null) user.updateEmail(request.email());
    return UserResponse.from(userRepository.save(user));
}
</code></pre>
<p>실무 기준: 프로필 전체 편집 화면 → PUT, 알림 토글 하나 → PATCH</p>
<h2>6. 전역 예외 처리: API 품질의 핵심</h2>
<p>에러 발생 시에도 일관된 JSON 응답을 반환해야 프론트엔드가 에러를 처리할 수 있습니다.</p>
<pre><code class="language-java">
public record ErrorResponse(String code, String message, List&lt;FieldError&gt; errors) {
    public record FieldError(String field, String message) {}
    public static ErrorResponse of(String code, String message) {
        return new ErrorResponse(code, message, List.of());
    }
}
</code></pre>
<pre><code class="language-java">
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity&lt;ErrorResponse&gt; handleValidation(MethodArgumentNotValidException e) {
        List&lt;ErrorResponse.FieldError&gt; fieldErrors = e.getBindingResult()
            .getFieldErrors().stream()
            .map(f -&gt; new ErrorResponse.FieldError(f.getField(), f.getDefaultMessage()))
            .toList();
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_ERROR", "요청값이 올바르지 않습니다.", fieldErrors));
    }

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity&lt;ErrorResponse&gt; handleNotFound(UserNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(ErrorResponse.of("NOT_FOUND", e.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity&lt;ErrorResponse&gt; handleUnexpected(Exception e) {
        log.error("Unexpected error", e);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(ErrorResponse.of("INTERNAL_ERROR", "서버 내부 오류가 발생했습니다."));
    }
}
</code></pre>
<p>검증 실패 시 응답 예시:</p>
<pre><code class="language-json">
{
  "code": "VALIDATION_ERROR",
  "message": "요청값이 올바르지 않습니다.",
  "errors": [

    {"field": "email", "message": "유효한 이메일을 입력하세요"}
  ]
}
</code></pre>

<h2>결론</h2>
<p>Spring Boot REST API의 품질은 규칙과 구조에서 나옵니다.</p>
<ul>
<li><strong>URL은 자원 중심</strong>, HTTP 메서드로 행위를 표현하세요</li>
<li><strong>DTO를 분리</strong>하여 엔티티를 직접 노출하지 마세요</li>
<li><strong><code>@Valid</code>로 검증</strong>하고, <code>@RestControllerAdvice</code>로 에러 응답을 통일하세요</li>
<li><strong>상태 코드를 정확히</strong> 사용하세요 (201, 204, 404)</li>
<li><strong>버전(<code>/api/v1</code>), 페이징, 에러 형식</strong>을 프로젝트 초기에 확정하세요</li>
</ul>
<p>이 규칙들을 먼저 고정하고 그 위에 기능을 쌓으면, API가 커져도 유지보수 비용이 폭발하지 않습니다.</p></article>
