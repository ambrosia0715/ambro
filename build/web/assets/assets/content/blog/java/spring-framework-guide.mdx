# 스프링 프레임워크(Spring Framework) 완전 정복: 개념, 구조, 사용방법

_작성일: 2026-02-09_

스프링 프레임워크(Spring Framework)는 자바 생태계에서 가장 널리 쓰이는 **애플리케이션 프레임워크**입니다. “스프링 = 웹 프레임워크”로 오해하는 경우가 많지만, 스프링의 본질은 웹이 아니라 **객체를 유연하게 조립하고(IOC/DI), 횡단 관심사를 분리하며(AOP), 계층형 애플리케이션 구성을 돕는 기반**에 있습니다. 이 글에서는 스프링의 핵심 개념과 구조를 짚고, 실제로 프로젝트에서 어떻게 쓰는지까지 연결해 보겠습니다.

![Spring Framework 개요](assets/images/blog/spring_framework_hero.webp)

## 1) 스프링의 핵심 개념 3가지

### (1) IoC/DI: 객체 생성과 연결을 “컨테이너”가 담당

스프링은 애플리케이션이 필요로 하는 객체(Bean)를 만들고, 의존 관계를 연결하는 역할을 **스프링 컨테이너**에게 위임합니다. 우리는 “어떤 구현이 필요하다”만 선언하고, 실제 조립은 컨테이너가 수행합니다.

```java
@Service
public class OrderService {
  private final PaymentClient paymentClient;

  public OrderService(PaymentClient paymentClient) {
    this.paymentClient = paymentClient;
  }
}
```

핵심은 **생성자 주입**처럼 의존성을 외부에서 받도록 설계하는 것입니다. 그러면 테스트에서 Fake/Mock을 주입하기 쉬워지고, 구현 교체도 쉬워집니다.

### (2) AOP: 로깅/트랜잭션 같은 “공통 관심사”를 분리

로깅, 권한 검사, 트랜잭션 같은 기능은 많은 곳에 반복됩니다. AOP(Aspect Oriented Programming)는 이런 코드를 비즈니스 로직에서 분리해 “붙였다 떼는” 방식으로 관리하게 해줍니다.

대표적으로 `@Transactional`은 **트랜잭션 경계를 선언**하고, 실제 구현은 스프링이 프록시를 통해 처리합니다.

### (3) PSA: 구현체가 바뀌어도 같은 방식으로 사용

스프링은 특정 기술(서블릿/리액티브/ORM 등)에 강하게 묶이지 않도록, 공통된 추상화(스프링 방식)를 제공합니다. 덕분에 JDBC → JPA로 바꾸거나, 서블릿 기반 → 리액티브로 넘어갈 때도 “스프링의 사용 방식”은 크게 유지됩니다.

## 2) 스프링의 구조: 어떤 모듈들이 있는가

스프링은 모듈형 구조로, 필요한 부분만 골라 쓸 수 있습니다.

- **Core Container**: IoC/DI의 중심(Bean, ApplicationContext)
- **AOP**: 프록시 기반 AOP 기능
- **Spring MVC**: 서블릿 기반 웹 프레임워크(Controller, DispatcherServlet)
- **Data Access**: JDBC 템플릿, 트랜잭션 추상화, ORM 연동 기반

이 중에서도 “스프링을 스프링답게 만드는” 핵심은 **Core Container**입니다.

## 3) 스프링 사용방법: 가장 기본적인 흐름

실무에서는 보통 스프링 부트를 쓰지만, 스프링 프레임워크의 구성 요소를 이해하려면 스프링 MVC의 동작 흐름을 한 번 정리해두면 도움이 됩니다.

### (1) 요청 처리 흐름(Spring MVC)

1. 클라이언트 요청이 들어오면 `DispatcherServlet`이 받습니다.
2. 요청 URL/메서드에 맞는 `@Controller` 메서드를 찾습니다.
3. 컨트롤러는 서비스/리포지토리를 호출해 결과를 만들고,
4. 스프링은 View 또는 JSON 응답으로 변환해 반환합니다.

```java
@RestController
public class HealthController {
  @GetMapping("/health")
  public Map<String, String> health() {
    return Map.of("status", "ok");
  }
}
```

### (2) 설정 방법(개념)

스프링은 전통적으로 설정이 다양합니다.

- XML 설정(레거시)
- Java Config(`@Configuration`, `@Bean`)
- 컴포넌트 스캔(`@Component`, `@Service`, `@Repository`)

최근에는 대부분 **Java Config + 컴포넌트 스캔** 조합을 사용합니다.

## 4) 실전 팁: 스프링을 “유지보수하기 쉽게” 쓰는 법

- **의존성은 인터페이스로**: 구현 교체/테스트가 쉬워집니다.
- **생성자 주입을 기본값으로**: 불변성 유지, 순환참조 조기 발견
- **트랜잭션 경계를 서비스 계층에**: 컨트롤러는 얇게, 서비스는 도메인 규칙 중심
- **AOP 남용 주의**: “마법”이 늘어나면 디버깅 비용이 커집니다.

## 결론

스프링 프레임워크는 단순히 웹을 만드는 도구가 아니라, **대규모 애플리케이션을 구조적으로 설계하고 확장 가능한 형태로 운영**하기 위한 기반입니다. IoC/DI, AOP, 모듈 구조를 이해하면 스프링 부트의 자동 설정이 “왜 편한지”도 더 선명하게 보입니다.
